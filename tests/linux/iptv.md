# IPTV qualification

`src/client/GuidePanel.test.tsx` mounts the shipped GuidePanel and Radix Select with React DOM and pinned Happy DOM. It drives the actual minute callback across local midnight, checks request boundaries and rendered airing identities, holds a response while the heading changes, and retains the chosen day offset. The Europe/Rome case crosses a 25-hour DST day. The group test selects the literal group `all`, another group, and All groups, checking both request values and rendered channel IDs. Each test restores DOM globals, fetch, timers, time and timezone. These component checks do not qualify browser layout or native input.

The generated red and blue H264 streams carry a video clock in their RGB pixels. Each frame has a fixed eight-bit guard, a 24-bit timestamp at 40 ms precision relative to the fixture epoch, and a second row containing the complement. The encoder receives the wall-clock timestamp when that frame is generated. Wall and monotonic clocks must agree within 100 ms. The marker is below the existing solid-color pixel sample and survives YUV420 conversion and scaling.

Encoding starts when guide qualification begins, after the earlier native suites. Two single-thread x264 encoders advertise six live segments per channel and retain generated segment files until fixture cleanup. FFmpeg's `delete_segments` expires old files by playlist duration even with a larger count threshold, which loses bytes needed by the twenty-second delayed window. Files have unique sequence names and atomic publication. The fixture stops accepting frame times after ten minutes, bounds its request log to 5000 entries, records hashes of served segments, and removes its temporary files and processes on cleanup. The official driver archives each exact served manifest after delayed-window rewriting, every advertised segment and their SHA-256 hashes under `iptv-streams` before responding. Those artifacts survive fixture cleanup. Archive errors remain in `failures.jsonl` and fail subsequent requests.

Run the local encoding regression with `bun test tests/linux/iptv-clock.test.ts`. It uses FFmpeg from PATH, or the exact executable in `COUCH_IPTV_FFMPEG`. `COUCH_IPTV_CLOCK_EVIDENCE` selects an optional JSON output path and places the raw archive beside it. The official Linux preflight uses `/artifacts/iptv-clock-preflight.json`, so failed archives survive container removal even if the test exits before writing the summary. Successful runs remove their temporary archives. The roughly forty-second test fetches real H264 segments, decodes them to a 1600x1000 letterboxed frame, checks advancing timestamps, loads a window twenty seconds behind, checks that all six advertised URLs return bytes matching their archived hashes, requires the same freshness assertion to fail, and restores the current window. This is local decoder evidence only.

The reserved native run uses the ordinary `bun run test:linux` entry point. After a phone requests Go live, `iptv-native-clock.ts` captures the actual X11 display. It requires a 1600x1000 native viewport at scale one, unchanged VideoStage geometry, and an RGB24 screenshot of exactly that size. An eight-pixel HTML origin mark verifies viewport alignment only. The timestamp is decoded exclusively from the H264 video area. Five-by-five interior samples require at least 23 unambiguous dark or light pixels in each cell; guard and complement checks reject missing, damaged or occluded markers.

Each capture records wall time before and after X11 capture, with a maximum one-second uncertainty interval and a monotonic clock cross-check. Given a decoded timestamp `T`, the conservative maximum lag is `captureEnd - T`. It must be at most 8000 ms. The minimum lag subtracts the 40 ms timestamp precision from `captureStart - T`. Decode time is outside the capture interval. PNG hashes, frame timestamps, intervals, lag bounds, encoder hash and fixture epoch are retained in `iptv.json`. Every capture first persists its raw geometry, wall/monotonic boundaries, process exit and PNG hash in a separate JSON file. It adds the decoded tick before returning. Raw frame pairs are written after each capture, before advancement, positive, negative or recovery assertions can fail. Instrumentation time remains inside the conservative capture interval.

The native positive case requires two advancing presented timestamps within the latency limit after pausing long enough for the source to move ahead. The negative control then reloads a real twenty-second delayed manifest window. Both frames must advance and be at least twenty seconds old. The same freshness assertion must reject them specifically for excess lag. Decode failures, a stalled frame, clock uncertainty or changed geometry cannot count as a successful negative control. A final current-window reload must pass again. The explicit host action re-probes current live eligibility and selects the newest complete segment; ordinary Play keeps normal buffering. The helper snapshots every request from the action boundary through the first observed new-playing state, before minimizing the phone window. This complete trace must contain one native blue manifest after the fresh host probe response, no earlier native segment, a first segment matching that manifest's newest, and no later older segment. HTTP requests have no playback ID, so this is a conservative ambiguity check rather than direct load attribution. Ambiguity fails startup qualification; the independent native 3 → 5 → 3 regression and presented-frame freshness remain separate requirements. Playback IDs, player position and HTTP requests remain diagnostic observations; they cannot satisfy presented-frame freshness.

After three more segment publications, the driver holds a native-requested blue segment for twelve seconds. Two late-hold captures must actually stop advancing. It releases delivery in `finally`, requires the same authoritative load to resume advancing pixels within twenty-five seconds, then checks an explicit Go live against the unchanged 8000 ms and 1000 ms limits. If the hold does not stall presentation, that check fails and its evidence remains. Separate held-segment controls require Stop and replacement playback to defeat late delivery.

The selected Rust `iptv_live_start` test compares actual ordinary, explicit-live and ordinary-again HLS requests, restores preexisting demuxer options, and loads ordinary local media after cancellation. Source review and that test do not establish full native freshness or stalled-feed acceptance.

Actual native positive/negative results, phone/tablet/desktop/TV screenshots, administrator flows, reconnect/restart and the authorized Apple sample remain required. A local H264 test does not qualify these flows or imply provider catch-up support. Hardware rendering and measured physical audio also remain outside software-only evidence.
