# Browser keep-awake and installation

Research checked 13 October 2026 against the specifications and browser vendors'
documentation. Screen Wake Lock can prevent an idle phone's screen from dimming
or locking while Couch is visible. Installing Couch as a web app is useful for
access and presentation, but does not itself keep the screen awake or guarantee
background execution. [1], [2], [8]

## What Couch already has

The application already has a PWA foundation in [vite.config.ts](../vite.config.ts):
a standalone manifest, 192px and 512px icons, a maskable icon, and an app-shell
service worker generated by `vite-plugin-pwa`. Its navigation fallback is limited
to frontend routes; API and WebSocket traffic stays on the network.
[register-sw.ts](../src/client/register-sw.ts) registers the worker only for
production browser clients in a secure context, skips native windows, and
handles registration failure. [index.html](../src/client/index.html) also supplies
an Apple touch icon. `apps/web` is the project website, not this remote client.

The practical installation gap is certificate trust: Couch's LAN listener uses
a self-signed certificate, and clicking past its warning does not make Chrome
accept it for service-worker registration or normal PWA installability checks.
Chromium explicitly checks certificate errors for both. See the existing
[controller guide](desktop-controllers.md) and [LAN setup](lan-origin.md). [6], [7]

## Keep the visible client awake

Use the built-in `navigator.wakeLock.request("screen")`, with no extra library.
It is exposed only in secure contexts, and the document must be fully active
and visible. Modern Chromium supports it; Safari added the API in 16.4. WebKit
specifically announced working **Home Screen web-app** support in iOS and iPadOS
18.4, so Safari-tab support must not be taken as proof that older installed iOS
web apps work. [1], [2], [3], [4]

Couch's browser behavior:

- A browser-local **Keep screen awake** preference in **Settings → Playback** is
  enabled by default for browser clients. It applies while this device is playing
  picture or sound and Couch is visible, including playback loading. Playback
  on a different device does not keep an idle controller awake. This is the
  chosen product scope. Keeping the screen on uses more battery.
- Check `window.isSecureContext` and `navigator.wakeLock` at runtime. Request one
  screen lock when enabled, visible, and this device has active playback; retain
  its sentinel to release it.
- Reacquire on `visibilitychange` when the page becomes visible. Release on
  opt-out, pause, stop, loss of local output or connection, and teardown. Clear
  the sentinel when its `release` event fires. Account for requests that finish
  after playback or the setting changes, or after teardown.
- Treat refusal and release as normal states. Show a short unavailable or
  released explanation; allow another attempt through the setting or when
  returning to Couch. Do not immediately loop requests after an OS release.

The browser or OS may deny or release a lock for low battery, power saving,
platform policy, or user preference. Hidden pages lose their screen locks.
The specification treats OS acquisition as advisory; even a returned sentinel
cannot promise that the screen will never sleep. Manual screen locking and
switching to another app remain under the user's control. Network heartbeats
are not a substitute for this screen-lock mechanism. [1], [2]

## Make the existing PWA dependable

Preserve the current manifest and app-shell worker. A PWA needs useful launch
metadata and suitable icons, but installation is distinct from offline caching:
Chrome removed the worker fetch-handler requirement for menu installation in
Chrome 108 on mobile and 112 on desktop, and its current documented promotion
criteria list HTTPS and manifest fields without requiring a worker. Installing
a generic website or creating a shortcut can also be offered under different
browser rules. Do not describe a worker as universally mandatory. [5]

On iOS/iPadOS, a manifest with `display: "standalone"` makes an added Home Screen
site open as a web app. Retain the Apple touch icon; WebKit gives it precedence
over manifest icons. For a future installation control, use the browser's
install event where supported and documented Add to Home Screen instructions
elsewhere. Installation remains a user action. [5], [9]

Trusted HTTPS is the next infrastructure requirement for a dependable LAN PWA.
Ordinary `http://192.168.x.x` or HTTP LAN hostnames are not secure contexts;
the HTTP loopback/`localhost` exception refers to the device running the browser,
not a remote Couch server. The `COUCH_ALLOW_HTTP=1` TV fallback therefore cannot
provide Screen Wake Lock. Adding a DNS name alone does not make the existing
certificate trusted. [10]

Plan trusted certificates separately from the keep-awake preference. The
[current LAN guide](lan-origin.md) describes publicly trusted certificates via
DNS validation or a private CA trusted by each client; custom certificate
loading and renewal are not implemented by the direct listener. Do not infer
wake-lock availability solely from a clicked-through certificate warning:
secure-context API exposure and Chrome's worker/install certificate checks are
different checks. Use the runtime capability check and handle request failure.
[6], [7], [10]

An installed app and its service worker do not keep a WebSocket, timer, or page
running indefinitely after the OS backgrounds or locks the device. Service
workers have event-driven lifetimes and may be terminated when idle. Couch still
needs its existing reconnect behavior, and the server must remain reachable for
control and playback; precaching the shell does not provide offline playback.
[1], [8]

## Device verification

Check Chrome on Android, Safari on iOS, and an iOS/iPadOS 18.4+ Home Screen app.
Use trusted HTTPS for the installation case. Verify idle-screen behavior during
local picture and sound playback, pause/stop, remote-only playback, opt-out,
disconnect, leaving and returning to the app, manual screen locking, and power
saving. Also check that plain LAN HTTP reports wake lock unavailable and that
the native desktop window does not acquire this browser-only lock. Automated
lifecycle tests can validate requests and releases, but cannot establish actual
phone power-management behavior.
