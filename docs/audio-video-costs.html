Three product behaviors. Buffers cost time. Codec conversions cost CPU. Sending a copy to each device costs bandwidth.

CPU hotspots below are architectural, not profiler measurements. Device limits are unknown unless explicitly stated.

Current scope: Direct can target any permitted single device. Prioritize synchronized live audio; new live video is deferred. Captured-media candidate diagrams below describe audio only. Relaxed screen sharing retains its current buffered A/V path until a replacement is agreed. Zones are future work.

Adding listeners still means sending more copies

WebRTC today
Publisher ── N stream copies ──→ receivers
1 encode → 1 decode per track/path. Publisher upload and peer work grow with listeners; encoder sharing is not guaranteed. No safe viewer ceiling is measured. TURN adds connectivity, not shared fanout.
Shared engine
Source ── 1 feed ──→ Core ── N copies ──→ receivers
Encode once per shared format. Core sends the copies; every receiver still decodes. The live source feed may be raw or encoded, depending on capture design.

Conditional WebRTC option: keep it for captured sources only if it demonstrates a meaningful latency advantage. It aligns A/V locally, but does not synchronize receivers. That advantage has not yet been established against the proposed engine.

How to read the timing and capacity evidence
  • The 100 ms concert goal is input-to-ear, not just network delay. Capture, packetization, codec lookahead, scheduling and hardware all consume it.
  • Latest source-clock work passed a 350 ms checkpoint on one wired receiver. R5 has passing 100/95 ms long runs; earlier revisions contain lower passes and later failures. This is not a repeatable phone/Wi-Fi guarantee.
  • Older 50-browser runs exercised real decoding with synthetic capture and virtual output. They do not prove physical speaker skew, radio capacity or synchronized video.
  • Current yt-dlp runs at most 3 extractions concurrently and queues up to 16. Pairing is limited to 20 attempts per minute. These constrain startup/join bursts, not the number of already-playing users.
  • More receivers multiply network/output work. More independent shared Playbacks also multiply Core decoding/encoding. More buffering mainly costs delay and memory; it is not the same thing as more codec CPU.
  • Clock resampling/correction is additional processing beyond the codec counts. Display refresh and OS/Bluetooth output delay are outside those counts.
