# Reassess the growing-recording backend

Checked 8 September 2026. This corrects the architectural assumption in the earlier [Ant investigation](timeshift-ant-community.md), without replacing its measurements or deleting implementation and evidence.

Tvheadend is Couch's existing TV/DVR integration. The owner clarified after the bounded preflight that no Tvheadend instance is currently deployed. Existing scheduling support remains in Couch. Ant is a provisional account-free candidate for reliable growing-recording delivery to the existing libmpv player. The owner's earlier answer to keep existing scheduling did **not** approve permanent Ant capture/storage ownership. No Ant replacement of Tvheadend, general media-backend role, installation or updater change follows from this investigation.

The evidence does not yet earn Ant a permanent place. It also does not establish that Tvheadend-only satisfies the required journey. Prefer Tvheadend-only if the missing bounded experiment succeeds with a reasonably small maintained integration. Otherwise present the measured advantage and narrow Ant responsibility for a separate owner decision. Windows controller verification is deferred by the owner and does not affect this comparison.

The owner has deferred growing-recording/chase-play because they will not use it for a while. It is outside this delivery, and further experiment preparation and runtime have stopped. No backend deployment or growing-playback architecture has been selected. Ant remains provisional; the full journey remains unaccepted. All implementation, fixtures and evidence are preserved. The comparison below records what was learned and what would remain if this feature is reopened.

## Smallest maintained paths worth comparing

1. **Tvheadend recording through existing HTTP/libmpv.** Keep the qualified scheduling, account, recording UUID and reporting owner. Ordinary `/dvrfile/UUID` has a bounded current-size response. FFmpeg's maintained HTTP reconnect options exist, but continuous reads, dynamic seek bounds and correct finality are unqualified; `reconnect_at_eof` alone treats every EOF as retryable and does not know DVR completion. Do not sell an option change as a solution without the full sequence. [Tvheadend HTTP implementation](https://github.com/tvheadend/tvheadend/blob/4ffbc07e6da1a0c0d5e8004f8ac72d701716c4cc/src/webui/webui.c), [FFmpeg protocols](https://ffmpeg.org/ffmpeg-protocols.html#http).
2. **Tvheadend plus maintained HTSP file reader.** The strongest current standalone client is HTSP **0.9.0**, with SDK core/playback **0.10.0**, verified in Maven Central today. The SDK follows one generation-bound recording across temporary EOF and validates finality. Its decoder/seek integration targets Android Media3, not libmpv. A small JVM-to-native byte bridge might suffice for a recording; this is a feasibility question, not a requirement to rebuild packet-level HTSP live streaming. The bridge would still own cancellation, seek/reopen coordination and same-file verification after connection loss. [Published HTSP](https://repo.maven.apache.org/maven2/at/bernhardberger/tvheadend/htsp/0.9.0/), [published SDK](https://repo.maven.apache.org/maven2/at/bernhardberger/tvheadend/sdk-core/0.10.0/), [current SDK contract](https://github.com/bernhardberger/tvheadend-sdk/blob/90ca12b92173c88be79dda3ed5a83f13f7e5b267/README.md).
3. **Tvheadend plus existing FFmpeg, if access to the actual recording file is available.** FFmpeg's supported `file:...` `follow=1` waits for appended bytes. First test direct libmpv access through maintained libavformat; dynamic time seeking and finality may still fail. If so, a bounded stream-copy EVENT remux of that same recording is a narrower alternative to Ant. It needs file identity/access, final drain, process lifetime and disposable-segment retention. It adds derivative media and custom coordination. The subsequent direct file-follow preflight passed only the limited seeks recorded below; no remux or production path was selected. A read-only local/shared recording mount is a real prerequisite, not permission to invent NAS deployment. [File protocol](https://ffmpeg.org/ffmpeg-protocols.html#file), [HLS muxer](https://ffmpeg.org/ffmpeg-formats.html#hls-2).
4. **Tvheadend plus Ant limited to delivery.** Tvheadend would remain the authority for input, guide, scheduling, recording identity and DVR storage. Ant would only create/serve EVENT segments for the selected recording if it demonstrates an advantage over the smaller paths. No tested Tvheadend-to-Ant handoff exists. The current adapter attaches independently created Ant broadcasts; it does not solve the incumbent “Record, then Play from beginning” journey. Keeping both independent recordings would need explicit duplicate-storage justification. [Provisional adapter commit](https://github.com/avoid-quest/couch/commit/3afb4bf45f0b65d542bceab0349c4173d345acc9), [vendor HLS recording](https://docs.antmedia.io/guides/recording-live-streams/hls-recording/).

Do not expand option 2 into a live HTSP packet muxer merely because the earlier research discussed one. libmpv's existing read/seek/size/cancel callback API is a possible byte boundary, with explicit cross-thread cancellation and EOF rules. Whether its demuxer updates growing TS seek bounds is the decisive missing experiment. [Pinned libmpv callback contract](https://github.com/mpv-player/mpv/blob/v0.37.0/libmpv/stream_cb.h).

## Experiments retained for a future scope decision

These are preserved research options, not active tasks. The owner has deferred the feature; resuming this work requires reopening its scope. Any later experiment should retain red runs and use bounded disposable resources. No T480 build or backend installation is implied.

1. Start with the retained real Tvheadend fixture, one pass-through TS recording and exact current packaged libmpv. Test HTTP and, only with an authorized read-only mount of that same file, maintained file-follow delivery. Record first-byte latency, original recording UUID/inode, current sizes, player playback ID/duration/position, pixels/audio clock and every seek/read. The pass signal is the full journey below, not “FFmpeg kept reading.” Stop an option-only approach at the first demonstrated unsupported dynamic seek/finality boundary rather than accumulating flags.
2. If direct delivery fails, choose **one** bounded feasibility comparison. Prefer the existing FFmpeg EVENT remux when the recording file is locally accessible; otherwise evaluate published JVM growing-reader bytes through the libmpv-provided callback API. Keep all glue in the throwaway fixture and count it. Do not build both infrastructures preemptively. Either result must include completion drain and stalled-read cancellation, and must not manufacture EOF to hide failure.
3. Replay the preserved Ant failure through updated actual Couch using identical delayed manifests/TS bytes and the reviewed EVENT reload setting. Then test a real producer interruption separately, including the retained 20-second timeout boundary. This distinguishes a client reload improvement from an Ant producer-recovery advantage. Tie the input to a real Tvheadend recording before claiming option 2 satisfies the product journey.
4. On the smallest surviving candidate, use the same generated recording to run: Record → earliest playable beginning → drain to growing edge → append on the same playback ID → backward seek → appended seek outside initial content → temporary producer interruption → separate transport interruption → genuine completion/final drain → near-end seek → Stop/reopen/resume. Verify profile progress before/after, no false watched/queue advance, two-controller state, backend/app restart stopped, pending Stop/replacement cancellation and bounded cleanup. Capture process CPU time, peak RSS, bytes on disk, bytes transferred and service failures with the same input/duration/limits. Record startup latency rather than inventing an acceptance threshold.
