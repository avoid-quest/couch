# GTK and libmpv rendering

Issue [#421](https://github.com/avoid-quest/couch/issues/421) asks whether GTK needs different mpv calls. This review covers source revision `423221134cd66606cbc0c69133f547780b4cef06`.

## Answer

No GTK-specific mpv command change is warranted. Couch should retain `vo=libmpv`, an OpenGL `mpv_render_context`, and a `GtkGLArea`. Replacing that with `wid` would make the Linux path X11-specific and would not fix the threading contract.

GTK's main thread may remain the render thread: libmpv recommends, but does not require, a separate render thread. The render header nevertheless makes use of a render thread conditional: it may not issue normal, non-safe calls on that mpv core or wait/lock on a thread that does. Couch currently makes synchronous control and property calls there, so it is outside that allowed set. Leaving `MPV_RENDER_PARAM_ADVANCED_CONTROL` unset avoids its stronger promise; it does not make those synchronous calls render-thread-safe.

## Contract and implementation

The Linux journey pins the Ubuntu 24.04 `libmpv2` 0.37 line ([its test asserts that version](../../tests/linux/replaygain.ts)); the official `v0.37.0` tag dereferences to [`818ce7c51a6b9179307950e919983e0909942098`](https://github.com/mpv-player/mpv/tree/818ce7c51a6b9179307950e919983e0909942098). On 22 September 2026, the checked current release was [`v0.41.0` / `41f6a645068483470267271e1d09966ca3b9f413`](https://github.com/mpv-player/mpv/tree/41f6a645068483470267271e1d09966ca3b9f413), and current `master` was [`69474527816bb7c00735806213f7a158ff5b2be0`](https://github.com/mpv-player/mpv/tree/69474527816bb7c00735806213f7a158ff5b2be0). The relevant threading and lifecycle text is materially unchanged between the pinned and checked current headers (the render-header diff only deprecates ambient light). See the [pinned threading contract](https://github.com/mpv-player/mpv/blob/818ce7c51a6b9179307950e919983e0909942098/libmpv/render.h#L55-L124) and the [checked-current contract](https://github.com/mpv-player/mpv/blob/69474527816bb7c00735806213f7a158ff5b2be0/include/mpv/render.h#L55-L124).

That contract requires serialized `mpv_render_*` calls; a current, identical OpenGL context for every render API call; no mpv call in either callback; no normal non-safe client call or wait dependency on the render thread; and destruction of the render context before its mpv handle. It recommends the render API over native-window embedding for GUI toolkits. The normal client API being generally thread-safe does not supersede this render-thread restriction: it serializes through the core lock. The explicitly safe render-thread alternatives include `mpv_command_async`, `mpv_set_property_async`, `mpv_get_property_async`, and `mpv_wait_event(..., 0)` ([client API](https://github.com/mpv-player/mpv/blob/69474527816bb7c00735806213f7a158ff5b2be0/include/mpv/client.h#L133-L140), [async commands](https://github.com/mpv-player/mpv/blob/69474527816bb7c00735806213f7a158ff5b2be0/include/mpv/client.h#L975-L996), [zero-timeout event polling](https://github.com/mpv-player/mpv/blob/69474527816bb7c00735806213f7a158ff5b2be0/include/mpv/client.h#L1689-L1720)).

Couch follows the lifecycle and OpenGL parts of that model in [`desktop.rs`](../../src-tauri/vendor/tauri-plugin-video/src/desktop.rs): it creates and realizes a `GtkGLArea`, makes its context current before creating the render context, sends the update callback through a one-item GLib channel, calls `update()` on the GTK thread with the context current, and renders the GTK framebuffer from `connect_render`. Drop removes the callbacks, makes the context current, then drops the render context before the mpv handle. The vendored `libmpv2` binding exposes each required operation: `RenderContext::new`, `set_update_callback`, `update`, `render`, `report_swap`, and `Drop`.

GTK 3 documents that `GtkGLArea` makes its GL context current during its `render` signal and manages the framebuffer used for its texture. See [GtkGLArea](https://docs.gtk.org/gtk3/class.GLArea.html) and its [render signal](https://docs.gtk.org/gtk3/signal.GLArea.render.html). This is the rendering arrangement Couch uses, not native-window embedding.

`wid` is the alternative mpv setup, not an extra rendering command. mpv documents it as an X11 window on Linux. GTK's current X11 surface accessor is deprecated for new code, and GTK 4 removed portable native/foreign subwindow support. See mpv's [`wid` option](https://mpv.io/manual/master/#options-wid), GTK's [X11 surface accessor](https://docs.gtk.org/gdk4-x11/method.X11Surface.get_xid.html), and the [GTK 3 to 4 migration guide](https://docs.gtk.org/gtk4/migrating-3to4.html#adapt-to-gdkwindow-api-changes). `wid` is therefore not a first-class Wayland-compatible replacement.

## Synchronous work in the GTK thread

All Linux native requests are dispatched through the GTK main context. `load_source` synchronously stops and replaces the source. `control` synchronously performs stop-adjacent work, seek and property writes, then takes a snapshot. `stats`, diagnostic reads and snapshots synchronously read mpv properties. Event draining uses `wait_event(0.0)` and has a 64-event bound, so it does not wait for an event but can consume GTK time under a hot event stream.

None of these calls occur inside the mpv update callback. The callback only tries to enqueue a redraw, which meets that narrower rule. The synchronous calls still share the render thread with `update()` and `render()`, outside the header's permitted set. mpv documents a possible deadlock, degraded playback after its timeout, and a `mpv_render_context_render() not being called or stuck` log. This is a documented contract violation, not a measured incident. In checked-current mpv implementation, that exact log means a pending frame was not consumed by `render` before its roughly 200 ms deadline and the frame is dropped; it is useful stuck-render evidence, but does not by itself prove a GTK freeze or API deadlock ([implementation evidence, not a public contract](https://github.com/mpv-player/mpv/blob/69474527816bb7c00735806213f7a158ff5b2be0/video/out/vo_libmpv.c#L504-L554)).

## Measurement status

The retained Linux journey exercises actual Tauri/libmpv playback under Xvfb with a GtkGLArea. The investigation added opt-in telemetry forwarding, command acknowledgement timing, a stuck-render scan, and an isolated artifact option. It also places a seek, Stop, and visible-source replacement before the journey's unrelated phone sections. The test keeps its default artifact directory; `COUCH_LINUX_ARTIFACTS` only selects an isolated directory for a concurrent investigation.

The reproducible evidence run used `COUCH_RELEASES_ENABLED=false TAURI_VIDEO_TELEMETRY=1 bun run test:linux` at [`34f72b7ff32bf25c5c54c91c574a00db3b25ce04`](https://github.com/avoid-quest/couch/commit/34f72b7ff32bf25c5c54c91c574a00db3b25ce04). Ubuntu 24.04 ARM64 reported mpv 0.37.0, `vo=libmpv`, software decode, and `gpu-dumb-mode=yes`. The actual GtkGLArea session acknowledged seek in 0.39 ms, Stop in 0.70 ms, replacement Play in 5.29 ms, and every subsequent measured command within 87.48 ms. `presented_frames` advanced from 3 to 15 with zero dropped frames, while telemetry reported nonzero 1.99 to 9.52 FPS samples. It emitted no `mpv_render_context_render() not being called or stuck` log.

That playback run then failed the pre-existing phone queue layout assertion for four long radio titles, before its later general-journey pixel and phone checks. This is neither a render failure nor evidence of a contract violation. It means the run is not a green full Linux qualification and does not qualify the new early native-pixel capture. The failure artifact records the exact assertion and revision. A subsequent `bun run test:linux --diagnostics` at [`52557a4a375631937e43b0a9acc98cb69e10276b`](https://github.com/avoid-quest/couch/commit/52557a4a375631937e43b0a9acc98cb69e10276b) passed the real diagnostic path: playback continued during collection, the export request took 1.69 ms, its own responsive 390px phone checks and screenshots passed, and no stuck-render log occurred.

The runs use Xvfb, software rendering, and a PulseAudio null sink. They do not make claims about a physical display, GPU decode, audio hardware, Wayland, HDR, HDMI, or a TV. The retained journey now has an early native-pixel capture after Stop and replacement, but concurrent Linux builds contended for the shared Cargo target volume before that revised run reached playback. That unrun hook is not evidence.

## Recommendation

Keep the GtkGLArea/libmpv render API integration. Do not add `wid` or `ADVANCED_CONTROL`. GTK requires its objects to be used on the main thread, while `GtkGLArea` makes its GL context current for `render` ([GTK threading](https://docs.gtk.org/gtk3/section-threading.html), [GLArea render](https://docs.gtk.org/gtk3/signal.GLArea.render.html)); those facts do not establish a separate-render-thread migration.

The exact remaining correction boundary is therefore narrow but not a one-line call substitution: either expose and use libmpv's declared-safe asynchronous command/property APIs, correlate their replies before publishing the affected snapshot, and retain zero-timeout event draining; or choose a separately owned GL context/render thread with no GTK wait dependency. The vendored `libmpv2` wrapper currently exposes synchronous `command`, `set_property`, and `get_property`, but documents no async wrappers ([binding inventory](../../src-tauri/vendor/libmpv2/bindings.md)). Merely moving those calls to a control thread is not compliant if GTK rendering waits for its result. The first route is the only source-supported small correction candidate; its acknowledgement/order semantics and the retained journey's measured outcome decide whether it is justified. No binding replacement or framework change is supported by this evidence.

No production correction is merged or included in this branch. Issue #421 should remain open: add the async binding wrappers and reply-correlated player state as one reviewable implementation, then rerun the isolated full Linux journey to a green result with the early native-pixel artifact. Choosing a dedicated GL render thread instead is a broader GTK/ownership redesign and needs an explicit architecture decision.
