# Kodi parity and reuse options

Research checked 2026-09-05. Scope: Linux mini PC connected to a TV, shared LAN control, music/radio, local/network libraries, Jellyfin, online services, real-time pub/sub control of one playback instance. Synchronized speaker output is a future option, not a v1 requirement. This is a product scope and architecture assessment, not a playback benchmark. Kodi's current stable release link resolves to [21.3 Omega](https://github.com/xbmc/xbmc/releases/tag/21.3-Omega). Development source and documentation also describe Kodi 22, so those establish implementation direction rather than guaranteed stable-platform behavior.

The product owns TV navigation, the library, queue, playback settings, shared session, errors, installation and updates. The current direction is one Tauri application with a Bun coordinator, SQLite and embedded native playback. Optional modules are managed internal dependencies with our controls and update flow, not scope exclusions or tools users must assemble.

Read [architecture and shared state](architecture.md), [playback](playback.md), and [provider integration](providers.md) alongside this scope. Release allocations below are proposed milestones, not claims of implemented support.

## Product capability matrix

"Core" includes the libraries Kodi ships/integrates. "Add-on/backend" means Kodi presents the feature through its own UI while another implementation supplies it. The proposed release allocation is an engineering recommendation, not an existing user-approved scope reduction. R1 is a useful native media center, R2 completes the agreed broader media-center scope, and R3 adds optional synchronized speakers. Multi-device video is outside the requested scope. Kodi replacement should not be advertised until the selected R2 gates pass.

Reuse labels identify work already available upstream, not verified support in this product. **Upstream candidate** means a documented engine, library or backend capability; **conditional** means the integration needs qualification; **no qualified path** means the current design does not establish support. The remaining work is identified as app UI/data, backend integration, or native integration. Every row still needs its product gate.

The implementation reuses the get-air Tauri video plugin for native composition. Small documented patches expose its existing native driver and add observations/settings needed by the shared session. The [playback assessment](playback.md) records the pinned source and release limits. Frame-accurate seeking and hardware output remain separate qualification work.

## Kodi reuse paths

| Path | Reuse and benefit | Cost and constraint | Judgment |
| --- | --- | --- | --- |
| Kodi distribution with a new TV skin and TS remote | Keeps playback, library, PVR, addons and platform work. Best path to broad existing parity quickly. | TV skin uses Kodi XML/navigation rules. A TS browser remote is supported, but this does not make the TV application TS. Underlying settings and addon-specific interactions remain. | Serious option if feature parity outranks implementation language. Start by reskinning rather than forking core. |
| Kodi core fork with replacement TV UI | Could preserve more addon/core behavior while changing application presentation. | Core C++, GUI/player/service dependencies, addon dialog/settings bindings, upstream merges and GPL distribution obligations. Replacing the GUI with React is engineering work, not a supported switch. | Consider only if new UI freedom plus Kodi addon compatibility are hard requirements and maintenance cost is accepted. |
| New app with embedded libmpv or GStreamer and TS product logic | Own the complete UI, library/session model, provider contracts and LAN UX; reuse mature decoding, timing and subtitle rendering. | Reuse the libraries/backends above and build their product behavior. Kodi addons and PVR clients cannot simply be loaded into Bun; a compatibility host is another substantial implementation. | Current preference: Tauri + embedded libmpv with TS product logic, subject to the native and provider gates. |
| TS frontend of a media server such as Jellyfin | Reuses library metadata/users/progress and optional transcoding. | Provides only the server's domain and supported source integrations; does not replace the Linux native player or arbitrary provider behavior. | Useful integration or ownership choice for library data, not a complete answer alone. |

Kodi's [README](https://github.com/xbmc/xbmc/blob/master/README.md) identifies C++ as the main implementation and Python/XML addons. Its [skin introduction](https://kodi.wiki/view/Skin_development_introduction) documents window XML, controls and navigation. The current [VideoPlayer](https://github.com/xbmc/xbmc/blob/master/xbmc/cores/VideoPlayer/VideoPlayer.cpp) directly depends on the application, GUI component, settings, rendering and windowing. From those dependencies, extracting a standalone "libkodi" is not a small reuse step; this is an architectural inference, not a benchmark. Public JSON-RPC is an integration interface for a running Kodi instance, not a video rendering library.

Kodi's [license](https://github.com/xbmc/xbmc/blob/master/LICENSE.md) is GPL-2.0-or-later, with additional component licenses noted. Preserve the relevant license/source obligations when distributing a fork; audit individual reused addons separately. Do not label this an all-TypeScript rewrite while retaining Kodi underneath.

## Build gates that preserve the ambition

1. Prove the integrated receiver. Native video and UI in the same Tauri application, subtitles/tracks/chapters/delays, phone and physical input, hardware decoding, HDR/refresh tests on target hardware, crash recovery. Verify the native wrapper exposes these controls and their observed state. A wrapper demo with play/pause is not this gate. Use representative difficult files as well as provider samples. This decides the native composition architecture before a polished catalog is built.
2. Deliver a media center. Local/NAS library, Jellyfin, radio/music queue, profiles/resume, offline behavior, metadata and ordinary TV navigation. Reuse media inspection/tag parsers, SQLite search and focus navigation. Run two-controller conflict/reconnect cases against actual observed playback state, including shared library updates and source switches with only one audible player.
3. Complete chosen Kodi parity. Music gapless/ReplayGain, collections, IPTV guide, backend DVR/timeshift, CEC/passthrough and all named providers. Measure open/play/seek/channel-switch delay and dropped frames. A PVR feature only passes when scheduling, cancellation, failure, live pause/seek and seeking a growing recording work from our UI. Each named provider records tested versions/content, controls, session expiry and explicit unsupported cases. Optional worker/backend installation does not remove these gates.
4. Optional future synchronized speakers. Keep output-device identity separate from controller identity in R1. Later add a synchronized audio transport without changing the shared library or queue model. Multi-device video and its synchronization are outside scope.

The first three gates are the proposed product scope. Gate four is a speaker expansion that requires an audio synchronization implementation. The current synchronization requirement is pub/sub application state across controllers of one playback instance. We should not trade away subtitles, library behavior, music continuity and TV integration merely to keep the first source-code tree small.
