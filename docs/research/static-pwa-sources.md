# Static PWA source feasibility

Checked 2026-09-27 against current code and primary documentation. “Static” means no Couch server or extraction proxy; third-party media servers still exist. This is a capability assessment, not a browser compatibility test of each upstream endpoint.

## What the browser boundary changes

A public, unauthenticated URL is not necessarily readable by browser JavaScript. Cross-origin metadata, HTML scraping, playlists and manifests need the upstream's CORS cooperation. `fetch(..., {mode: "no-cors"})` produces an opaque response, not readable JSON or HTML. A worker cannot remove that boundary. Browser-controlled headers such as `Origin`, `Cookie` and `Referer` cannot be copied from arbitrary extraction output as ordinary headers. [Fetch standard](https://fetch.spec.whatwg.org/#http-cors-protocol).

A direct progressive URL can nevertheless play through `<audio src>` or `<video src>` without granting JavaScript access to its response bytes, subject to browser format support and server policy. That does not make the source's catalog or ICY metadata readable. [HTML media resource fetching](https://html.spec.whatwg.org/multipage/media.html#concept-media-load-resource).

HLS via hls.js needs CORS for every fetched resource, including manifests, segments and keys; native HLS availability is a separate capability. HTTPS pages also encounter mixed-content upgrading/blocking for HTTP media, especially IP-address URLs. [hls.js requirements](https://github.com/video-dev/hls.js#cors), [browser mixed-content behavior](https://developer.mozilla.org/en-US/docs/Web/Security/Defenses/Mixed_content).

## What a native helper earns

[web-media.ts](../../src/server/web-media.ts) does substantially more than forwarding a URL: extraction, metadata, format selection, separate audio/video URLs, transport headers, DASH manifest substitution and limited expiry recovery. [yt-dlp.ts](../../src/server/yt-dlp.ts) launches a subprocess with runtime/plugin configuration. Upstream yt-dlp documents a command-line/Python system and JavaScript-runtime dependencies; there is no first-class browser drop-in here. [yt-dlp documentation](https://github.com/yt-dlp/yt-dlp#dependencies).

The helper therefore earns broad website extraction and native playback compatibility, not merely LAN discovery. It does not promise DRM, region-restricted or signed-in content: current extraction explicitly rejects unsupported cases. Browser-side queues, favorites, history, direct sources and suitable catalogs can move independently. Embeds need a distinct renderer adapter and capability model: Couch can translate exposed play/pause/seek events, but cannot assume its native tracks, quality controls, media URLs or exact handoff semantics. A handoff can reopen an identity and best-effort position where the provider API permits it.

## Existing PWA prerequisites

[vite.config.ts](../../vite.config.ts) already emits a manifest, root-scoped worker and static assets into `dist`; the worker precaches only the app shell. [register-sw.ts](../../src/client/register-sw.ts) requires a secure browser context and skips native/development use. Static hosting needs HTTPS, correct root paths and initial-navigation SPA fallback; service-worker caching alone does not supply server data. [Service Worker specification](https://w3c.github.io/ServiceWorker/).

The UI still assumes Core: [session.ts](../../src/client/session/session.ts) discovers `/api/connection`, checks build/identity and connects `/api/ws`; [AppShell.tsx](../../src/client/sections/shell/AppShell.tsx) gates content on pairing. A standalone browser session/store and browser renderer are prerequisites, not a deployment flag. [scripts/build.ts](../../scripts/build.ts) additionally compiles the Bun sidecar; a static-only build should use the Vite graph independently. Existing `web:build` targets the separate Astro marketing/download site, not this application.
