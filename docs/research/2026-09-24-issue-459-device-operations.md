# Device operations for Desktop Full

Checked 24 September 2026 for [#459](https://github.com/avoid-quest/couch/issues/459) against main `95971aa4`, the issue body and [latest owner policy](https://github.com/avoid-quest/couch/issues/459#issuecomment-5802989656). The owner accepted "Check in System Settings" for demonstrated infeasible operations on the selected playback host. The later task handoff says a Windows machine is now available; the issue's earlier "no Windows machine" premise is stale. This is a source and API map, not a new hardware receipt.

## Bluetooth

| Operation | Linux host | macOS host | Windows host |
| --- | --- | --- | --- |
| Inventory, discovery, power | [BlueZ adapter](https://github.com/bluez/bluez/blob/master/doc/org.bluez.Adapter.rst) supports powered state, discovery and release. Couch uses `bluer` and reports absent, blocked and off separately in [`bluetooth.rs`](../../src-tauri/src/bluetooth.rs). | Public [`IOBluetoothDeviceInquiry`](https://developer.apple.com/documentation/iobluetooth/iobluetoothdeviceinquiry) starts and stops Classic inquiry; Couch reports controller absence and power state in [`bluetooth_macos.rs`](../../src-tauri/src/bluetooth_macos.rs). No supported public power setter was found in the checked Apple API, so Couch hands that action to host System Settings. | WinRT [`Radio`](https://learn.microsoft.com/en-us/uwp/api/windows.devices.radios.radio?view=winrt-26100) exposes enumeration and state. State changes require `RequestAccessAsync`, can prompt locally, and must be verified after `SetStateAsync`; hardware and policy can deny them. Couch currently has only the non-Linux/non-Mac error stub in [`bluetooth.rs`](../../src-tauri/src/bluetooth.rs), so Windows discovery/power are unfinished adapters, not established platform limits. |
| Pair, prompts, cancel | [BlueZ Device1](https://github.com/bluez/bluez/blob/master/doc/org.bluez.Device.rst) and [Agent1](https://github.com/bluez/bluez/blob/master/doc/org.bluez.Agent.rst) cover pair, PIN, passkey, confirmation and display. Couch scopes its temporary agent to one selected device and expires owner, operation and prompt tokens. | [`IOBluetoothDevicePair`](https://developer.apple.com/documentation/iobluetooth/iobluetoothdevicepair) supports an app pairing UI, PIN reply, numeric confirmation and stop. Its [delegate](https://developer.apple.com/documentation/iobluetooth/iobluetoothdevicepairdelegate) also receives passkey display. The checked public pair class has no numeric passkey entry reply; that ceremony needs a tested fallback. Couch has callback and cancellation code, but no new physical pairing receipt. | [`DeviceInformationPairing`](https://learn.microsoft.com/en-us/uwp/api/windows.devices.enumeration.deviceinformationpairing?view=winrt-26100) has custom pairing and `UnpairAsync` on association endpoint objects. Microsoft's [sample](https://learn.microsoft.com/en-us/samples/microsoft/windows-universal-samples/deviceenumerationandpairing/) uses that object kind, and Microsoft says [WinRT Bluetooth APIs work from Win32](https://learn.microsoft.com/en-us/windows/uwp/devices-sensors/bluetooth-dev-faq). The current Couch Windows adapter does not use them. Consent, prompt ownership and cancellation need a real target check; do not assume a remote request can satisfy a local Windows prompt. |
| Connect, disconnect, forget | [BlueZ Device1](https://github.com/bluez/bluez/blob/master/doc/org.bluez.Device.rst) connects/disconnects; [Adapter1.RemoveDevice](https://github.com/bluez/bluez/blob/master/doc/org.bluez.Adapter.rst) removes a bond. Couch reads back state and keeps selected audio separate from connection. | Public [`IOBluetoothDevice.openConnection`](https://developer.apple.com/documentation/iobluetooth/iobluetoothdevice/openconnection%28_%3A%29) opens a baseband link; that alone does not prove an active audio profile. Couch also closes and reads back the link. The owner's existing C39S connect/disconnect trial had one stale disconnect readback, so repeat verification matters. No public bond-removal operation was established in the checked API; Couch's Forget action gives the accepted host-settings guidance. | Pair/unpair APIs exist, but Windows outgoing headset audio connection and explicit disconnection remain unresolved. RFCOMM service access is not an A2DP route. Couch's error stub does not demonstrate a Windows limitation. Require a Bluetooth headset plus audio endpoint readback on the available Windows machine before deciding a fallback. |

Apple requires a [Bluetooth usage description](https://developer.apple.com/documentation/bundleresources/information-property-list/nsbluetoothalwaysusagedescription); the bundle declares one. Couch separately reports denied/restricted permission, absent controller and off power. On Linux, BlueZ plus the active user audio session need `bluez`, `libspa-0.2-bluetooth`, PipeWire/Pulse and WirePlumber as described in [`docs/bluetooth.md`](../bluetooth.md). The Bluetooth API's connected flag is never proof that Couch owns an audible output.

## Sound output

| Operation | Linux host | macOS host | Windows host |
| --- | --- | --- | --- |
| Select, default, route, loss | [`pactl`](https://manpages.ubuntu.com/manpages/noble/man1/pactl.1.html) manages sinks and defaults through PipeWire's [Pulse protocol](https://docs.pipewire.org/page_module_protocol_pulse.html); libmpv pins a selected sink. [`sound-routing.ts`](../../src/server/sound-routing.ts) saves selection, checks the observed stream, and interrupts playback on loss. | [Core Audio](https://developer.apple.com/documentation/coreaudio/) exposes output devices and [default output](https://developer.apple.com/documentation/coreaudio/kaudiohardwarepropertydefaultoutputdevice). Couch's [`sound.m`](../../src-tauri/src/sound.m) writes and reads those properties and checks the player process route. The Mac prototype observed automatic default-output change on Bluetooth connection, so installed checks must prove saved intent is reconciled. | [MMDevice](https://learn.microsoft.com/en-us/windows/win32/api/mmdeviceapi/nn-mmdeviceapi-immdeviceenumerator) enumerates endpoints and reads the default, and [WASAPI stream routing](https://learn.microsoft.com/en-us/windows/win32/coreaudio/getting-the-default-device-endpoint-for-stream-routing) permits a specific endpoint ID. The cited public MMDevice interface has no default setter. Couch currently disables `systemAudio` on Windows in [`hub.ts`](../../src/server/hub.ts), so output selection and loss handling are unfinished even though native libmpv playback exists. A public system-default write path still needs proof or a bounded fallback decision. |
| Test, delay, volume, mute | Couch's three-second `paplay` stereo test checks the requested stream route, and delay is saved through the shared API. `pactl` sets sink volume, mute and card profile; hardware audibility remains a separate check. | Couch's shared API and [`sound-mac.ts`](../../src/server/sound-mac.ts) run the same test through mpv, save delay, and read/write effective output volume and mute through Core Audio. It reports per-output writability using [`AudioObjectIsPropertySettable`](https://developer.apple.com/documentation/coreaudio/audioobjectispropertysettable%28_%3A_%3A_%3A%29) and exposes only available output data sources. The owner reported basic C39S audibility and later manual Mac audio passes on #459; those are owner reports, not installed artifact receipts. | [`IAudioEndpointVolume`](https://learn.microsoft.com/en-us/windows/win32/api/endpointvolume/nn-endpointvolume-iaudioendpointvolume) provides endpoint volume, mute and notifications. Couch has no Windows system-audio backend, test tone or output profile implementation. Delay remains a shared saved preference, but its effect on an installed Windows player needs a media check. Endpoint properties and applicable configurations must be measured on the target. |

The shared [`BluetoothSettings.tsx`](../../src/client/sections/settings/device/BluetoothSettings.tsx) and [`SoundSettings.tsx`](../../src/client/sections/settings/device/SoundSettings.tsx) already use the paired Administrator host API. The implementation gap is beneath that contract. In particular, the generic Windows Bluetooth and sound errors should not be presented as a demonstrated platform restriction. The selected playback host must appear in any permission or settings guidance.

## Exact outstanding installed gates

- **Windows.** On the available installed Windows host, inventory a real Bluetooth adapter and headset; try discovery, supported pairing consent and cancellation, connect/disconnect, unpair only a disposable bond, and observe whether an audio endpoint appears. Test actual output selection, volume/mute, hardware keys, stereo audibility, output loss in playing/paused/loading/live states, explicit resume, saved selection and restart. Record Windows build/architecture, installer and app revision, permissions and hardware IDs. The current adapters must be implemented before these can pass.
- **Mac.** Use the installed bundle with Bluetooth permission and the existing C39S bond intact. Recheck connect/disconnect readback, automatic default changes, remote selection and volume/mute, output loss and restart. A fresh pair/PIN/passkey/Forget trial requires an owner-selected disposable device; the owner explicitly deferred another physical pairing before Preview, not a Full claim. Preserve the owner-reported audio passes as reports rather than inventing per-case receipts.
- **Linux.** Installed AppImage on broad X11 and Wayland user sessions with active BlueZ/PipeWire/WirePlumber and real output hardware. Prove discovery/ceremonies, selected output ownership, physical stereo sound, external volume/mute, HDMI/analog or available output-only profiles, loss without audible fallback or autoplay, and restart/reconnect. The earlier disposable Debian 12 X11 AppImage extraction proves decoded audio and video in a virtual display; it does not prove FUSE installation, Bluetooth radio, hardware output or Wayland.

Use the accepted settings message only for the Mac public API gaps and any later **demonstrated** target limitation. A missing adapter, absent hardware or unrun installed check stays open evidence, not a pass.
